# 你的方案评估：飞书入口 + 云端 Agent + 数据闭环

## 总体判断

**架构选对了，而且飞书入口带来一个你可能没意识到的巨大红利：会话统计天然完备。**桌面端 Agent(如 Claude Code)跑在用户机器上，遥测要靠上报、会丢数据；而飞书机器人模式下，**每一条会话必然流经你的服务器**——你的“拿到所有会话进行统计”不是附加功能，是架构自带的。这个闭环里每一环都有现成技术，没有需要发明的东西，主要工作量在工程整合。

## 闭环架构(具体到组件)

```
【飞书】自建应用/机器人(长连接接收事件)
   │  用户身份、部门/角色(通讯录 API)、交互卡片、审批流
   ▼
【接入层】事件入队(im.message.receive_v1 → 消息队列)→ 3 秒内 ack
   ▼
【Agent 运行时】Claude Agent SDK worker 池
   │  ├─ Skill 目录(.claude/skills/,中央版本下发)
   │  ├─ 飞书官方 MCP(lark-openapi-mcp:消息/文档/多维表格/审批)
   │  ├─ 自研 in-process 业务工具(@tool:ERP/CRM/WMS 查询与写入)
   │  └─ 权限引擎(按飞书角色决定工具白名单 + Skill 可见性)
   ▼
【全量事件流】每轮对话的结构化流水(用户输入/回复文本/工具调用及参数/token/耗时)
   ├─→ Langfuse(实时 trace、调试、失败 case 沉淀回归集)
   └─→ 审计库(不可变存储:谁、何时、问了什么、调了什么工具、动了什么数据)
   ▼
【优化闭环】周度失败分析 → 修订 SKILL.md → Promptfoo 回归门禁
   → git 打版本 → 按部门/租户灰度下发 → 指标对比 → 全量
```

## 各环节落地点

**飞书侧**：事件订阅选[「长连接接收事件」](https://docs.useknowme.com)(WSClient 模式，不用公网 IP、不用配回调加密，开发期省很多事)；交互卡片做结构化输出和「👍/👎/确认执行」按钮——**卡片的负反馈按钮就是你遥测体系里最廉价、最真实的质量信号**；高危操作直接跳[飞书审批流](https://github.com/larksuite/lark-openapi-mcp)(官方 MCP 自带 approval 预设)，审批结果回调 Agent 继续执行——客户不需要改变审批习惯，你的“确认门”零教育成本。

**云端运行时**：飞书事件要求快速 ack,所以必须“入队 → worker 异步跑 → API 主动推送”的异步形态；长任务先发“处理中”卡片再更新结果。会话用 SDK 的 session resume 按 `chat_id` 绑定，多轮上下文不断。**一个关键安全决策：云端多租户环境里，默认禁用 SDK 的 Bash 和文件写工具(`tools: []` 后只留你的业务工具)，Skill 读取走你控制的目录**——云端给一线用户开 shell 等于把服务器交出去，这条红线要在架构期定死。

**统计与优化**：北极星指标就一个——无干预完成率(卡片确认完成 ÷ 总任务)，辅助看 skill 触发命中率、工具调用成功率、负反馈率、每任务 token 成本。失败 case 用 Langfuse 从 trace 里挖，进回归集，这是整个闭环里唯一需要人工智力投入的环节，也是你产品的核心迭代动作。

**审计**：每次工具调用的参数和结果摘要全量落不可变存储。审计不是合规摆设——它同时是你的“效果计费”依据(证明这个工单是 Agent 独立完成的)和事故复盘的证据链。

## 三个必须尽早拍板的问题

**① 模型合规(最大现实约束)。**飞书用户就是国内用户，而 Anthropic API 不对大陆提供服务。三条路：**(a)** 网关转国产已备案模型(DeepSeek/Qwen/GLM),SDK 指向兼容端点——技术上可行，但多步工具循环的质量必须用你自己的评测集实测，不能想当然；**(b)** 运行时部署境外用 Claude——涉及数据出境的 PIPL 合规和延迟；**(c)** 混合路由，常规场景国产、复杂场景升级。我的建议：**M1 就把评测集建起来，用同一套 skill 在两三个模型上跑分，让数据替你做这个决策。**

**② 自建应用还是 ISV。**飞书自建应用 = 服务单个企业(客户自己开后台、授权给你)，上线最快；ISV 服务商模式 = 你做一个应用装进多家客户，多租户隔离、`tenant_key` 管理、应用市场审核都要做。建议 **M1/M2 用自建应用在 1–2 家种子客户跑通闭环，M3 再转 ISV**——别一开始就背多租户的复杂度。

**③ 数据边界协议。**一线会话里全是业务敏感数据(客户信息、成本、工艺参数)，统计和优化意味着这些数据回流给你。种子客户阶段就要把“数据用于 skill 优化”写进协议并做脱敏，否则闭环在法务那里就断了。

## 分期建议

- **M1(3–4 周)**：飞书机器人 + SDK worker + 3–5 个手写 skill + 全量事件流水入库 + 卡片反馈按钮。目标：种子部门真用起来，攒出第一批失败 case。
- **M2(1–2 月)**：权限引擎(角色→工具白名单)、审计库、Promptfoo 评测门禁、按部门灰度。目标：闭环从“人肉运营”变成“流水线”。
- **M3(3 月+)**:ISV 多租户、对接客户 ERP、模型路线定版、对外备案。

这个方案没有技术上的未知数，成败在运营密度——每周有没有人真的在看失败 case、改 skill、看指标变化。如果你要动手，我可以直接在当前目录把 M1 的脚手架搭出来(飞书长连接接入 + Agent SDK worker + skill 目录 + 事件流水表结构)，你说一声就开始。
